# PostgreSQL fresh-provisioning compatibility

AutoSQL supports the same managed PostgreSQL provisioning lifecycle on
PostgreSQL 14, 15, 16, 17, and 18. The version matrix proves adoption of an
existing schema, provisioning its managed projection into an empty target,
apply and semantic reinspection, a converged no-op, and an unrelated
incremental change.

## Supported managed projection

| Capability | Adopt and inspect | Create from empty | Incremental changes |
| --- | --- | --- | --- |
| Schemas, enums, domains, and sequences | Yes | Yes | Per negotiated driver operations |
| Permanent, non-partitioned tables and columns | Yes | Yes | Yes |
| Parameterized column types, arrays, and enum/domain types | Yes | Yes | Safe type changes only |
| Bounded PostgreSQL defaults, including casts, arrays, `now()`, UUID generation, and exact `nextval` references | Yes | Yes | Yes |
| `GENERATED ALWAYS` and `GENERATED BY DEFAULT` identity columns | Yes | Yes | Identity-mode alteration is fail-closed |
| Stored generated columns with exact column and routine dependencies | Yes | Yes | Creation only; generated-expression alteration is fail-closed |
| Comments on managed schemas, types, sequences, tables, columns, views, and materialized views | Yes | Yes | Add, replace, and remove |
| Provable views and materialized views | Yes | Yes | Within the bounded projection grammar |

The stored-generated expression grammar is structural and fail-closed. It
accepts literals, column references, bounded casts and arrays, and exact
immutable SQL function calls declared by dependency edges. It does not pass
arbitrary PostgreSQL expressions through to execution. Calls with same-name
overloads currently fail closed because AutoSQL does not guess PostgreSQL's
argument-type resolution from a declared edge.

## External and read-only boundary

Functions used by stored generated columns are explicit external
prerequisites. AutoSQL fingerprints the inspected function and
`postgres.VerifyGeneratedRoutinePrerequisites` verifies that the same routine
is present before planning. AutoSQL does not create or replace arbitrary
routine bodies.

Extensions, composite types, primary and unique constraints, check and foreign
key constraints, indexes, functions, procedures, triggers, policies, roles,
grants, memberships, and default privileges remain inspectable but read-only.
They can be adopted without drift, but must be provisioned by a separate owner
when creating a new target. `postgres.PreflightProvisioning` reports all such
objects and external prerequisites together, alongside any unsupported managed
metadata or semantics.

An “empty target” therefore means an empty **managed projection** with declared
external prerequisites already installed. This boundary prevents AutoSQL from
silently executing inspected routine bodies or taking ownership of database
security and extension objects.

## Executable evidence

- `TestCompleteCellProvisioningParity` exercises the complete lifecycle and
  explicit boundary in `pkg/postgres/plan_integration_test.go`.
- `.github/workflows/zdm-postgres-matrix.yml` runs that test on PostgreSQL
  14–18.
- `examples/hcl-postgres/generated.hcl` demonstrates both identity modes,
  comments, advanced defaults, and a stored generated column with exact
  dependencies.

## Release-note wording

Use this scope when announcing the capability:

> Fresh PostgreSQL provisioning now preserves the complete managed schema
> projection on PostgreSQL 14–18, including comments, parameterized and array
> types, bounded defaults, enums/domains, sequences, both identity modes, and
> stored generated columns. Generated-column routines remain fingerprinted
> external prerequisites; constraints, indexes, routines, extensions, and
> security objects remain inspectable/read-only and are reported together by
> provisioning preflight.
